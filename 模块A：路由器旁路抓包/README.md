## 1. 项目背景

《洛克王国：世界》把精灵资产收在背包里，但游戏没有导出能力。上级项目 `Roco-dashboard` 里有一份真实玩家 Miffy 的快照：

- **26 个盒子、593 只精灵**
- 其中 **187 只异色、84 只炫彩**

要看「我有哪些异色」「哪个盒子快满了」，只能一页页翻。数据明明存在，却不可查询——这就是整条链路要解决的起点。

## 2. 需求

我要的不是「翻得更快」，而是把游戏里不可见的数据变成可结构化查询的资产，同时守住三条硬约束：

- **不改游戏**：不碰进程、不注入、不改内存
- **不增加终端负担**：PC / iPad / 手机都不装驱动、不装证书
- **数据归用户**：默认不同步，交付物只含派生字段，原始帧与会话密钥不进产物

## 3. 现有方案

### 3.1 Windows：Npcap / WinPcap

- 要在**每台 PC 上安装内核态驱动**并给管理员权限；受管机器往往直接禁止安装，驱动本身也是高权限攻击面
- 只能看到装了驱动的那一台设备；换一台电脑就要再装一遍、再配一遍

### 3.2 安卓 / iOS：VPN 代理或 root / 越狱

- 代理类工具（Charles、HttpCanary、Stream 等）要装证书、开系统 VPN，明文流量经过第三方进程；App 侧还有证书绑定 / SSL Pinning 检测，经常抓不到或要额外绕过
- root / 越狱后跑 `tcpdump` 会破坏系统沙箱，安全边界和门槛都落在玩家手机上
- 多设备同样是每机一套：PC、iPad、手机各配各的，时间线对不齐，导出格式也不统一

## 4. 痛点

把上面的方案放进真实场景，问题不是「抓不到」，而是**代价放错了地方**：

| 维度 | 现有方案的问题 |
|---|---|
| 安全性 | 内核驱动要管理员权限；代理要装证书、明文过第三方进程；root / 越狱破坏沙箱 |
| 多设备 | 每台设备单独装、单独配，时间线对不齐，导出格式不统一 |
| 数据复用 | 每个工具只解决一个点，抓到的原始数据无法沉淀成统一数据源，上层应用要重复造轮子 |

结论：抓包能力是分散的，玩家和设备却要为每次抓包重复付成本。

## 5. 我是怎么解决的

把抓包点从终端设备搬到**网络必经点——路由器**：

1. 在 `br-lan` 上开混杂模式，BPF 严格过滤 `tcp port 8195 and host <游戏设备IP>`
2. 抓包进程**只写 pcap、不做解析**；离线回放时再重组 → 解密 → 按 opcode 门控解析
3. 会话密钥 `0x1002` 只在 TCP 建连瞬间下发，所以真实前提是**先开采集，再让设备断网 3 秒重连**
4. 只输出派生 JSON；原始帧、明文帧、会话密钥不进产物，默认不同步

底层已验证环境：**新路由 D2（Newifi D2）+ Padavan（老毛子）固件**。Entware 提供 `tcpdump` / `python3`，`/opt` 固定 256MB tmpfs，端点侧零安装。

这样一次抓包就能多处派生：

- **战斗读取**：opcode 4886 战斗帧，按 `battle_mode` / `enter_battle_type` 门控，只留需要的战斗事件
- **背包管理**：4934 / 6273 / 6275 / 6277 / 6289 解出 PetData 与 PetBox，生成 boxes JSON
- **图鉴收藏**：形态、异色、资质等字段继续派生到图鉴与毕业进度
- 以后加新应用，只新增离线解析器，**不用再动抓包链路，也不用重新配置任何终端设备**

设计上的三个判断：

| 判断 | 为什么重要 |
|---|---|
| **被动只读 + BPF 严格过滤** | 合规底线：不发包、不注入、不改内存，把「辅助工具」和「外挂」划清界限 |
| **抓包/解析拆分** | 同步解析大帧会拖垮抓包、导致战斗帧丢失；拆成「先抓后解」后互不干扰 |
| **默认不同步 + 字段白名单** | 数据所有权归用户；契约层不夹带 UID、玩家名、IP、时间戳——隐私最小化是设计约束，不是补丁 |

## 6. 实现过程中的困难

1. **同步解析拖垮抓包**：早期一边抓一边解，大帧到来时抓包进程被拖慢，战斗帧 4886 丢失
2. **密钥只在建连瞬间出现**：`0x1002` 不在后续流量里重发，采集晚开就解不开任何业务帧
3. **丢段与噪声帧**：默认 `gap_timeout=5s` 时 120 秒内 `link_lost` 74 次，战斗帧时有时无；1044 心跳约 14 条/秒，几分钟就把 5000 条 ring buffer 灌满，把 4886 挤出去
4. **多设备与双开**：PC、iPad、手机同时在线；同 IP 双开时仅靠 IP 无法区分会话
5. **路由器环境不稳**：Padavan 的启动脚本会在 USB 重挂时把 `/opt` 从 256MB 打回 40MB，Entware / `python3` 全丢
6. **盒位判别**：出战栏不是背包盒；场景宝箱 24 格与背包盒 30 格混在一起；协议里的 `box_id` 顺序也不等于游戏显示顺序

## 7. 怎么克服

1. **先抓后解**：抓包进程零解析只落 pcap，解析放到离线回放，两条链路互不干扰
2. **采集先行 + 断网重连**：先开采集，再让游戏断网 3 秒重连，确保拿到 `0x1002`
3. **放宽 gap_timeout + 分层留档**：`gap_timeout` 从 5s 调到 10s，`link_lost` 74 → 10、单场战斗 4886 帧稳定到 3；实时链路过滤 1044 心跳等无信息帧，但原始 pcap 完整留档，可通过开关恢复读取被忽略的 opcode
4. **按 IP 分发 + game_id 区分会话**：用 `--game-pc-ip` / `--game-ips` 锁定设备；258 解 profile 拿 `game_id`，同 IP 双开靠它区分
5. **固化路由环境**：改 `Sh01_mountopt.sh` + `nvram size_tmpfs=262144` + `started_script.sh` remount，并用 `mtd_storage.sh save` 写进 flash；另备一键恢复脚本应对意外重挂
6. **盒位判别式 + 队伍序列还原**：只认 `box_id∈[1,200]` 且 `len(pet_gids)==30` 且空位在 `[0,30]`；再从抓包 rawProtocol 的队伍变更帧恢复 3 队 × 6 的 Z 序。109 份历史抓包验证 108 份完美、1 份接近

## 8. 最终效果

- **数据结果**：Miffy 快照还原为 26 盒 / 593 只 / 187 异色 / 84 炫彩，玩家核心资产第一次可查询
- **链路结果**：PC + iPad + 手机统一采集；同一份 pcap 可派生战斗、背包、图鉴等多套应用
- **演进结果**：新增上层应用只写离线解析器，不再改抓包链路、不再配终端设备
- **安全结果**：端点零安装；交付物只有白名单派生字段；原始帧与密钥不出本机

- **链路演示**：6 个可点击节点（旁路抓包 → TCP 重组 → 会话解密 → opcode 门控 → 字段白名单 → 结构化快照），每个节点说明「做了什么 / 为什么这么设计」
