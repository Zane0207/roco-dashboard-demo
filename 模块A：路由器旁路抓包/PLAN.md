# 模块 A 实施计划：路由器旁路抓包 → 背包自动同步

> 本文件是模块 A 的实施依据：先按计划收敛交互与数据口径，再逐项完成验证清单。
> 同目录下的 `index.html` / `data.js` / `scripts/` 为现有草稿，在本轮实现中按需完善，不推倒重来。

## 1. 模块定位（面试叙事）

- **一句话**：观察真实玩家的背包数据不可查询，设计在网络必经点被动读取流量，把不可见的游戏数据变成可结构化查询的资产。
- **要证明的能力**：idea（从数据中发现问题）+ 产品判断力（合规、隐私、架构取舍）+ vibecoding（把想法快速变成可交互原型）。
- **讲述节奏**：痛点 30 秒 → idea 与三个取舍 60 秒 → 链路演示 60 秒 → 数据结果 30 秒 → 边界说明 20 秒。

## 2. 痛点（基于已确认的真实数据）

- Miffy 快照：**26 盒 / 593 只精灵 / 187 异色 / 84 炫彩**
- 游戏内无导出能力，玩家只能逐页翻看
- 本质问题：不是「记录效率低」，而是**玩家核心资产不可查询**
- 现有方案的边界：
  - Windows Npcap / WinPcap：每台 PC 装内核驱动、要管理员权限；受管机器常禁止，且只覆盖那一台设备
  - 安卓 / iOS：VPN 代理要装证书、明文过第三方进程且可能被 SSL Pinning 拦；root / 越狱破坏沙箱；多设备每机一套、时间线对不齐

## 3. Idea 与三个产品判断

| 判断 | 决策 | 理由 |
|---|---|---|
| 合规 | 被动只读 + BPF 严格 `tcp port 8195 and host <游戏设备IP>` | 不发包、不注入，划清辅助工具与外挂的界限 |
| 架构 | 抓包与解析拆分（先落 pcap，离线回放解析） | 真实踩坑：同步解析大帧会拖垮抓包、导致战斗帧丢失 |
| 隐私 | 默认不同步 + 字段白名单 | 数据所有权归用户；契约层不带 UID / 玩家名 / IP / 时间戳 |

## 4. 技术方案（取自上级项目真源文档）

底层已验证环境：**新路由 D2（Newifi D2）+ Padavan 固件**，`br-lan` 混杂模式 + Entware 的 `tcpdump` / `python3`，`/opt` tmpfs 固定 256MB；端点侧零安装。

链路 6 步，每步都要在 demo 中解释「做了什么 / 为什么」：

1. **旁路抓包**：`br-lan` 镜像 + libpcap + BPF 过滤
2. **TCP 重组**：按 flow 拼段，`gap_timeout` 兜底丢段
3. **会话解密**：`0x1002` 密钥只在建连瞬间下发 → 必须先开采集再断网 3 秒重连
4. **opcode 门控**：258 解 profile 拿 game_id；4934 解 PetData；6273/6275/6277/6289 解 PetBox；其余跳过
5. **字段白名单**：protobuf 只取数值与固定 kind，名字仅本地 catalog 还原
6. **结构化快照**：按 uid 攒会话（同 IP 双开靠 game_id 区分），静默 8 秒落盘 boxes JSON

- **交互组件**：
  - 6 步链路节点，点击展开设计决策
  - 「播放完整链路」带时间戳的模拟日志

- **不做**：真实 libpcap、云函数、完整 12 页签看板
